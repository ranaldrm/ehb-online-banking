## Browser walkthrough

Do all of this using only the browser UI (clicks and forms — no manual URLs):

1. Open the home page.
2. See the seeded accounts listed.
3. See the seeded businesses listed.
4. Open a business and view its accounts.
5. Open an account and note its balance.
6. View its transaction history (an account with none should say so clearly).
7. Make a deposit; confirm the redirected page shows the new balance and a new
   `INCOMING` transaction.
8. Make a valid withdrawal; confirm the updated state.
9. Make a valid payment between two **GBP** accounts (`1111` → `4444`); then open
   both accounts and confirm the source dropped, the target rose, and both have
   new transactions.
10. Deliberately trigger a failure: withdraw more than the balance, or pay across
    mismatched currencies. Confirm the UI shows a readable message and the
    account state stays valid (no half-completed change).

## Architecture checkpoint — explain the deposit flow

Be able to narrate what happens, end to end, when a user deposits money:

```text
Browser GETs the account page
        ↓
Spring MVC routes GET → @Controller method
        ↓
Controller asks AccountService for the account + transactions
        ↓
Controller puts them in the Model
        ↓
Thymeleaf renders the HTML
        ↓
Browser displays the page

User submits the deposit form
        ↓
Browser sends an HTTP POST with the form fields
        ↓
Spring MVC routes POST → @Controller method
        ↓
Controller reads accountNumber (@PathVariable) + amount (@RequestParam)
        ↓
Controller calls AccountService.deposit(...)
        ↓
Service loads the Account from the repository
        ↓
Account's domain method applies the rules (positive amount, etc.)
        ↓
Controller returns "redirect:/accounts/{number}"
        ↓
Browser performs a fresh GET
        ↓
Thymeleaf renders the now-updated state
```

And contrast the two output styles over the same services:

```text
REST:         Controller → DTO → Jackson → JSON
Thymeleaf UI: Controller → Model → Thymeleaf → HTML
```

## Completion criteria

Stage 2.5 is complete when:

- every main banking operation can be done in the browser;
- no JavaScript is needed for normal use;
- no CSS or frontend framework was introduced;
- the REST API still works;
- both REST and UI controllers reuse the service layer;
- banking rules live in the domain/service, not in HTML or controllers;
- no database has been added yet;
- `mvn test` is green;
- you can confidently explain `@Controller`, `Model`, templates, `th:text`,
  `th:each`, `th:href`, HTML forms, `@RequestParam`, and POST/Redirect/GET;
- the UI is crude but genuinely usable.

A suitable commit message:

```text
Add minimal Thymeleaf banking UI
```

---

## What's next

Stage 3 replaces the in-memory repositories with JPA + PostgreSQL. A key thing to
notice: because the UI talks to the **services** (not to storage directly),
swapping the storage underneath should barely touch the UI at all. That is the
payoff of keeping the layers clean throughout this stage.
