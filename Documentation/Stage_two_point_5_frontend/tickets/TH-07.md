# EHB Ticket TH-07 — Browse Businesses and Their Accounts

## Objective

Add a page that lists the seeded businesses, and lets you click one to see its
details and its accounts.

---

## Background for beginners

### Why this page matters

Each business has an ID, but those IDs are **random UUIDs generated at startup**
(look at `BusinessRepository` — the IDs change every time the app restarts). You
can't memorise or hard-code them. So the UI must *list* the businesses and let
you click through, carrying the current ID in the link. This is exactly the
`th:each` + `th:href` pattern from TH-04 and TH-05.

### The service methods you need

`BusinessService` provides:

```java
List<Business> getAllBusinesses()
Business       getBusinessByID(String id)          // throws BusinessNotFoundException if missing
Map<String,Account> getAccountsForBusiness(String id)
```

Map results to the display records:

- `BusinessResponse` has fields: `businessID`, `businessName`, `accounts`
  (a `List<AccountResponse>`). Use `BusinessResponse.from(business)`.
- For the accounts, reuse `AccountResponse` as in TH-04.

> **Security detail — do not leak the password.** A `Business` has a plaintext
> `password` field. `BusinessResponse` deliberately does **not** include it.
> Keep it that way: never add the password to the model or the template. This is
> a small example of "only expose display-safe fields at the presentation
> boundary".

> **Architecture detail.** As always: inject `BusinessService` into the
> controller, not `BusinessRepository`.

---

## Worked example (a *departments* page, so you build the businesses one)

**List controller:**

```java
@GetMapping("/departments")
public String departments(Model model) {
    List<DepartmentResponse> depts = departmentService.getAll()
            .stream().map(DepartmentResponse::from).toList();
    model.addAttribute("departments", depts);
    return "departments";
}
```

**List template with click-through links:**

```html
<ul>
    <li th:each="dept : ${departments}">
        <a th:href="@{/departments/{id}(id=${dept.id})}" th:text="${dept.name}">name</a>
    </li>
</ul>
```

**Details controller + template** follow the same pattern as the account details
page in TH-05, except you also loop over the department's members.

---

## Your task

1. Read `BusinessService`, the `BusinessResponse` record, and
   `BusinessController` to see how businesses are already mapped on the REST side.
2. Add a `GET /businesses` page in `UIController` that lists all businesses by
   name, each name linking to `/businesses/{id}` (use the current `businessID`
   from the data in the link).
3. Add a `GET /businesses/{id}` page that shows:
   - the business name;
   - the business ID;
   - its accounts (account number / currency / balance), looped with `th:each`.
4. Never display the password.

## Verify

- Open `/businesses`. You should see three businesses: `Dodgy Dave's`,
  `University of Brigadoon`, and `workShy Consultants LLC`.
- Click each. `Dodgy Dave's` should show accounts `1111` and `2222`;
  `University of Brigadoon` → `3333`, `4444`; `workShy Consultants LLC` → `5555`.
- **Restart the application** and repeat. The business IDs in the URLs will be
  different UUIDs, but the UI still works because it got the current IDs from the
  listing rather than hard-coding them. (If anything is hard-coded, this is where
  it breaks.)

## Concepts practised

- reusing another service from the UI layer;
- carrying unstable identifiers through links instead of hard-coding them;
- deliberately omitting a sensitive field at the presentation boundary.

## Done when

- businesses list and link through to a working details page;
- a restart does not break the navigation;
- the password is never shown.
