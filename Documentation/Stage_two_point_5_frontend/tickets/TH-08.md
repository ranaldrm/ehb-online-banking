# EHB Ticket TH-08 — Add a Deposit Form

## Objective

Let the user type an amount on an account page and deposit it, using a plain
HTML form and a Spring MVC POST handler. No JavaScript.

This is the biggest conceptual jump in the stage. Read the background slowly.

---

## Background for beginners

### HTML forms send data with a POST request

A `<form>` collects user input and sends it to the server when submitted:

```html
<form action="/some/path" method="post">
    <input type="text" name="amount" />
    <button type="submit">Go</button>
</form>
```

- `method="post"` → the browser sends an HTTP **POST** (GET is for fetching
  pages; POST is for changing something).
- `action="/some/path"` → where the POST goes.
- each `<input name="...">` becomes a **form parameter** sent in the request
  body, keyed by its `name`.

### Reading form parameters with `@RequestParam`

On the server, a POST handler reads each named field with `@RequestParam`:

```java
@PostMapping("/some/path")
public String handle(@RequestParam String amount) { ... }
```

Spring matches the method parameter name to the `name` of the form field. It can
also convert types for you — ask for a `BigDecimal` and Spring parses the text
into one:

```java
@PostMapping("/some/path")
public String handle(@RequestParam BigDecimal amount) { ... }
```

> **Note:** this is a *different* input style from your REST API. REST reads JSON
> from a `@RequestBody` DTO. An HTML form sends `application/x-www-form-urlencoded`
> fields, which you read with `@RequestParam`. Both end up calling the same
> service.

### POST / Redirect / GET — the pattern you must use

After a successful change, **do not render a page directly from the POST
handler.** Instead, tell the browser to go (redirect) to a normal GET page:

```java
return "redirect:/accounts/1111";
```

Why? If the POST handler rendered the page itself, the browser would remember
"the last thing I did was POST". If the user then hits refresh, the browser
re-sends the POST — **depositing again**. By redirecting to a GET page, a
refresh just re-runs a harmless GET. This is the classic
**POST → Redirect → GET** pattern.

```text
form POST → controller does the work → redirect → browser does a fresh GET → page shows new state
```

### The service call

Reuse the existing banking logic — do not re-implement deposit rules in the
controller:

```java
accountService.deposit(accountNumber, amount);   // returns a Transaction
```

## Worked example (a *top-up* form, so you build the deposit one)

**Form on the details page (`th:action` builds the URL from data):**

```html
<form th:action="@{/products/{id}/restock(id=${product.id})}" method="post">
    <label>Quantity:
        <input type="text" name="quantity" />
    </label>
    <button type="submit">Restock</button>
</form>
```

**POST handler:**

```java
@PostMapping("/products/{id}/restock")
public String restock(@PathVariable String id,
                      @RequestParam int quantity) {
    productService.restock(id, quantity);
    return "redirect:/products/" + id;   // Redirect/GET: safe to refresh
}
```

Note how the account/product is identified by the `@PathVariable` in the URL,
while the amount comes from a `@RequestParam` form field.

## Your task

1. On `account-details.html`, add a deposit `<form>` with `method="post"`:
   - its `th:action` should post to a deposit URL that includes the account
     number (e.g. `/accounts/{accountNumber}/deposit`);
   - it needs one input for the amount.
2. Add a `@PostMapping` handler in `UIController` for that URL:
   - take the account number as a `@PathVariable`;
   - take the amount as a `@RequestParam BigDecimal`;
   - call `accountService.deposit(accountNumber, amount)`;
   - return a `redirect:` back to the account details page.
3. Do **not** duplicate deposit rules (positive amount etc.) in the controller —
   the domain already enforces them.

> **Scope warning:** you do not need a form-backing DTO or `@ModelAttribute` for
> a single field. Two `@RequestParam`s are clearer here. Keep it small.

## Verify

1. Open account `1111` (balance 500.00). Note the balance.
2. Deposit, say, `50`.
3. You should land back on the account page (via the redirect) with balance
   `550.00` and a new `INCOMING` transaction in the history.
4. **Press refresh.** The amount must NOT be deposited a second time (if it is,
   you rendered from the POST instead of redirecting — fix that).

## Concepts practised

- HTML `<form>` + `method="post"`;
- `@RequestParam` and automatic type conversion to `BigDecimal`;
- POST/Redirect/GET and why it prevents double submission;
- reusing `AccountService.deposit` rather than re-coding the rule.

## Done when

- a deposit updates the balance and history;
- after the deposit you are back on the (GET) account page;
- refreshing does not deposit again.
