# EHB Ticket TH-09 — Add a Withdrawal Form

## Objective

Add a withdrawal form to the account page. This is the same pattern as the
deposit form, so it should feel much quicker.

---

## Background for beginners

You already learned everything you need in TH-08. The shape is identical:

```text
form POST → controller @PostMapping → service call → redirect → GET
```

The only change is which service method you call:

```java
accountService.withdraw(accountNumber, amount);   // instead of deposit(...)
```

The domain still owns the rules. In particular:

- withdrawing a non-positive amount throws `NonPositiveAmountException`;
- withdrawing more than the balance throws `ExceedsBalanceException`.

**Do not** re-check "is there enough money?" in your controller or hide the
button with HTML logic as if that were the real guard. The domain is the
authority. For now a failed withdrawal will throw and produce an ugly error
page — that is expected, and TH-10 fixes the presentation of errors.

---

## Worked example (reusing the TH-08 shape)

**Form:**

```html
<form th:action="@{/accounts/{num}/withdraw(num=${account.accountNumber})}" method="post">
    <label>Amount:
        <input type="text" name="amount" />
    </label>
    <button type="submit">Withdraw</button>
</form>
```

**Handler (mirror of the deposit one):**

```java
@PostMapping("/accounts/{accountNumber}/withdraw")
public String withdraw(@PathVariable String accountNumber,
                       @RequestParam BigDecimal amount) {
    accountService.withdraw(accountNumber, amount);
    return "redirect:/accounts/" + accountNumber;
}
```

---

## Your task

1. Add a withdrawal `<form>` to `account-details.html`, posting to a withdraw
   URL that carries the account number.
2. Add the matching `@PostMapping` handler that calls
   `accountService.withdraw(...)` and redirects back to the account page.

> **Resist the urge to abstract.** Deposit and withdraw look almost identical.
> Do **not** build a generic "form processor" to share the two. Two small, clear
> methods are better than one clever abstraction in a learning project this size.
> (This is a deliberate design-restraint exercise.)

## Verify

- **Valid withdrawal:** on account `1111` (balance 500.00), withdraw `100`. You
  should land back on the page with balance `400.00` and a new `OUTGOING`
  transaction.
- **Invalid withdrawal:** try to withdraw more than the balance (e.g. `99999`).
  Right now this will produce an unfriendly error page or stack trace. Note what
  happens — TH-10 is specifically about turning that into a readable message.

## Concepts practised

- recognising and reusing an established pattern;
- keeping banking rules in the domain;
- resisting premature abstraction.

## Done when

- a valid withdrawal updates balance and history and returns you to the page;
- an invalid withdrawal does not corrupt the account (balance unchanged).
