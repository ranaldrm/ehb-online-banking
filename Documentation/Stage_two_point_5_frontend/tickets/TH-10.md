# EHB Ticket TH-10 — Show Friendly Form Errors

## Objective

When a deposit or withdrawal fails (non-positive amount, or more than the
balance), show the user a short, readable message on an HTML page instead of a
stack trace or a JSON error.

---

## Background for beginners

### Why the existing handler doesn't help here

Your project already has `GlobalExceptionHandler`. But look closely: it is
annotated `@RestControllerAdvice`. That means it produces **JSON** error
responses — perfect for the REST API, useless for a browser page. If a browser
form triggers a banking exception, that advice would try to send JSON, which is
not a nice user-facing HTML page.

So the HTML UI needs its **own** small error handling. You must **not** change
or remove the REST `GlobalExceptionHandler` — the REST API still needs it.

### The exceptions you will catch

Both come from the domain and extend `BankingException`:

- `NonPositiveAmountException` — amount was zero or negative;
- `ExceedsBalanceException` — withdrawal bigger than the balance.

### Three possible approaches (pick the simplest that works)

1. **Catch in the controller + flash attribute (recommended for this UI).**
   Wrap the service call in `try/catch`, and on failure put a message where the
   redirected page can show it. Because you use POST/Redirect/GET, a normal
   model attribute would be lost across the redirect — so use a **flash
   attribute**, which survives exactly one redirect:

   ```java
   @PostMapping("/accounts/{accountNumber}/withdraw")
   public String withdraw(@PathVariable String accountNumber,
                          @RequestParam BigDecimal amount,
                          RedirectAttributes redirectAttributes) {
       try {
           accountService.withdraw(accountNumber, amount);
       } catch (BankingException ex) {
           redirectAttributes.addFlashAttribute("error", ex.getMessage());
       }
       return "redirect:/accounts/" + accountNumber;
   }
   ```

   Then in `account-details.html`:

   ```html
   <p th:if="${error}" th:text="${error}">error message</p>
   ```

2. **A tiny MVC `@ControllerAdvice`** (not `@RestControllerAdvice`) that catches
   `BankingException` and returns an error view. This is cleaner if you have many
   handlers, but it is more machinery than this small UI needs yet.

3. **Catch and re-render an error template** directly. Simple, but loses the nice
   refresh-safety of redirect.

> **Ask before going bigger.** If you feel tempted to build anything more
> elaborate than approach 1, pause and reconsider — the UI is deliberately tiny.

### What a flash attribute is

`RedirectAttributes.addFlashAttribute(...)` stashes a value in the session for
the duration of **one** redirect. After the redirected GET renders, it's gone.
That is exactly right for a one-off "that didn't work" message that should not
reappear on later page loads.

---

## Your task

1. Decide on an approach (approach 1 is recommended).
2. Make a failed deposit or withdrawal result in a short message appearing on the
   account page, with the account state unchanged.
3. Keep the banking rules in the domain/service — you are only improving how the
   failure is *presented*, not where it is *decided*.
4. Do not touch the REST `GlobalExceptionHandler`.

## Verify

Deliberately trigger each failure from the browser:

- deposit or withdraw a non-positive amount (e.g. `0` or `-5`) →
  `NonPositiveAmountException`;
- withdraw more than the balance →
  `ExceedsBalanceException`.

In both cases the page should show a readable message, remain usable, and the
balance should be unchanged. A successful operation afterwards should *not* still
show the old error (that is what the flash attribute guarantees).

## Concepts practised

- why a `@RestControllerAdvice` is wrong for an HTML flow;
- `try/catch` of a domain exception at the presentation boundary;
- `RedirectAttributes` flash attributes surviving a redirect;
- keeping the solution proportionate.

## Done when

- a non-positive amount and an over-balance withdrawal both show a clear message;
- the account state stays valid;
- the REST error handling is untouched.
