# EHB Ticket TH-11 — Add the Payment Form

## Objective

Add a page with a form that moves money from one account to another, choosing
both accounts from drop-downs populated with the real seeded accounts.

---

## Background for beginners

### Drop-downs built from data

An HTML `<select>` is a drop-down; each choice is an `<option>`:

```html
<select name="source">
    <option value="1111">1111 (GBP)</option>
    <option value="2222">2222 (EUR)</option>
</select>
```

- the `value` is what gets submitted;
- the text between the tags is what the user sees.

You don't want to hand-type the options — generate one `<option>` per account
with `th:each`, setting the submitted value with `th:value` and the label with
`th:text`:

```html
<option th:each="acc : ${accounts}"
        th:value="${acc.accountNumber}"
        th:text="${acc.accountNumber + ' (' + acc.currency + ')'}">
</option>
```

### The service call

`PaymentService` already does the work. Its signature is:

```java
Payment processPayment(String sendingAccountNumber,
                       String targetAccountNumber,
                       BigDecimal amount)
```

Call it directly from the UI controller. Do **not** re-validate the payment in
the controller — the service and domain already enforce the rules (positive
amount, sufficient funds, matching currency, etc.).

### Form data vs JSON — the contrast to understand

```text
REST API:   JSON  → Jackson → PaymentRequest record → PaymentService
HTML form:  form fields → @RequestParam parameters → PaymentService
```

Different front doors, **same** `PaymentService`. That is the whole point of
keeping logic in the service layer.

## Worked example (a *transfer-stock* form, so you build the payment one)

**Controller — show the form (needs the account list for the drop-downs):**

```java
@GetMapping("/transfer")
public String transferForm(Model model) {
    List<WarehouseResponse> warehouses = warehouseService.getAll()
            .stream().map(WarehouseResponse::from).toList();
    model.addAttribute("warehouses", warehouses);
    return "transfer";
}
```

**Template:**

```html
<form th:action="@{/transfer}" method="post">
    <select name="from">
        <option th:each="w : ${warehouses}"
                th:value="${w.id}" th:text="${w.name}"></option>
    </select>
    <select name="to">
        <option th:each="w : ${warehouses}"
                th:value="${w.id}" th:text="${w.name}"></option>
    </select>
    <input type="text" name="quantity" />
    <button type="submit">Transfer</button>
</form>
```

**Controller — handle the submit:**

```java
@PostMapping("/transfer")
public String transfer(@RequestParam String from,
                       @RequestParam String to,
                       @RequestParam int quantity) {
    warehouseService.transfer(from, to, quantity);
    return "redirect:/transfer";
}
```

## Your task

1. Read `PaymentService`, `PaymentRequest`, `PaymentResponse`, and
   `PaymentController` to see how the REST side does payments.
2. Add a `GET` page in `UIController` that shows a payment form. Put the list of
   accounts (as `AccountResponse`s) in the model so you can build the drop-downs.
3. The form needs: a source `<select>`, a target `<select>`, an amount input,
   and a submit button.
4. Add the `@PostMapping` handler. Read the three fields with `@RequestParam`,
   call `paymentService.processPayment(source, target, amount)`, then redirect
   somewhere sensible (back to the form, or to the source account page).
5. Reuse the error-handling approach from TH-10 so a failed payment (e.g.
   insufficient funds or mismatched currency) shows a readable message.

## Verify

- Make a valid payment between two **GBP** accounts: `1111` → `4444` for `50`.
  Afterwards, open each account page: `1111`'s balance should have dropped and
  `4444`'s risen, with matching new transactions on each.
- Try a failing payment, e.g. a currency mismatch (`1111` GBP → `2222` EUR) or
  an amount larger than the source balance, and confirm the UI reports it
  sensibly rather than crashing.

## Concepts practised

- `th:each` inside `<option>`, with `th:value` and `th:text`;
- building server-rendered form controls from data;
- form-field binding via `@RequestParam` vs JSON binding in REST;
- one service feeding two presentation layers.

## Done when

- a valid payment moves money and records transactions on both accounts;
- a failing payment is reported without a crash.
