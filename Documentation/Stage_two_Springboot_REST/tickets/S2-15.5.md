# Ticket S2-15.5 --- Add a Deposit Endpoint

## Context

This ticket was not planned in advance. It arose after S2-15 when a
deposit endpoint was added to `AccountController` outside the original
ticket scope.

The deposit feature required:

- a new request DTO (`DepositRequest`);
- a new `deposit` method in `AccountService`;
- a new POST endpoint in `AccountController`.

The response reuses the existing `TransactionResponse` DTO introduced
in S2-09, since a deposit produces a `Transaction`.

## What Was Built

### `DepositRequest.java`

A request DTO for incoming deposit data.

```java
public record DepositRequest(
    @NotBlank
    String accountNumber,
    @Positive
    @NotNull
    BigDecimal depositAmount
) {}
```

The field is named `depositAmount` rather than `amount` to be explicit
about what the value represents. The accessor is therefore
`depositAmount()`, not `amount()`.

### `AccountService.deposit(...)`

A new service method that retrieves the account by number and delegates
to the existing `Account.deposit(BigDecimal)` domain method.

```java
public Transaction deposit(String accountNumber, BigDecimal amount) {
    Account account = getAccountByNumber(accountNumber);
    return account.deposit(amount);
}
```

The service does not implement any deposit logic itself. It orchestrates
the use case and lets the domain do the work.

### `AccountController` — POST `/api/accounts`

A new POST endpoint added to the existing `AccountController`.

```java
@PostMapping
public TransactionResponse deposit(@Valid @RequestBody DepositRequest depositRequest) {
    Transaction transaction = accountService.deposit(
        depositRequest.accountNumber(),
        depositRequest.depositAmount()
    );
    return TransactionResponse.from(transaction);
}
```

`@Valid` triggers the `@NotBlank` and `@Positive` / `@NotNull`
constraints on `DepositRequest` before the method body runs.

The response reuses `TransactionResponse` rather than creating a
dedicated `DepositResponse`, because the result of a deposit is already
well represented by a transaction.

## Endpoint Summary

```
POST /api/accounts
Content-Type: application/json

{
  "accountNumber": "ACC001",
  "depositAmount": 200.00
}
```

Successful response:

```json
{
  "identifier": "...",
  "transactionType": "CREDIT",
  "transactionAmount": 200.00,
  "timestamp": "2026-09-26T10:00:00"
}
```

## Design Notes

- The endpoint lives on `AccountController` at `POST /api/accounts`
  rather than a dedicated `/api/deposits` path, since a deposit is an
  operation on an account.
- An alternative design would be `POST /api/accounts/{accountNumber}/deposits`,
  which would remove the account number from the request body. That is a
  reasonable alternative to consider.
- The response returns `200 OK` by default. `201 Created` is a
  reasonable alternative for an endpoint that creates a transaction
  record, but HTTP status refinement is outside the current ticket scope.

## Definition of Done

- `POST /api/accounts` accepts a JSON deposit request.
- `@Valid` rejects structurally invalid requests.
- The service delegates to the existing `Account.deposit(...)` domain method.
- A `TransactionResponse` is returned.
- Existing GET endpoints on `AccountController` are unaffected.
