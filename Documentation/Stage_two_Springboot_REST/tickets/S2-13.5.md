# Ticket S2-13.5 --- Fix Currency Design in the Payment Domain Model

## Context

This ticket was not planned in advance. It arose during the implementation
of S2-13 when wiring `CurrencyMatchValidator` inside `AccountRepository`
produced a compilation error:

```
constructor CurrencyMatchValidator in class CurrencyMatchValidator
cannot be applied to given types;
  required: Currency
  found:    no arguments
```

Investigating the error revealed a deeper design gap: `Payment` had no
`Currency` field, which meant `CurrencyMatchValidator` was comparing
`account.getCurrency()` against a currency baked in at construction time —
ignoring the `payment` parameter entirely. This is not meaningful
validation.

## What Changed

### `Payment.java`

Added `Currency` as a required constructor parameter and field, with a
`getCurrency()` getter and a null guard matching the existing validation
pattern.

A `Payment` now carries its own currency, which is intrinsic to what an
amount means. A payment for £100 and a payment for €100 are different
things.

### `Account.java` — `processOutgoingPayment`

Updated the `Payment` constructor call to pass `this.currency`, so the
source account asserts the currency of the payment it initiates.

### `CurrencyMatchValidator.java`

Removed the constructor argument. The validator is now stateless, like
`SufficientFundsValidator`. It compares `payment.getCurrency()` against
`account.getCurrency()` directly — which is the meaningful check.

### `AccountRepository.java`

`new CurrencyMatchValidator()` now compiles without arguments, which
was the original error.

### `PaymentResponse.java`

Added `Currency currency` to the response record so the API exposes
the payment's currency to the client.

### `BankingSystem.java`

Updated the Stage 1 demo to remove the currency argument from
`CurrencyMatchValidator` construction and to pass `Currency.GBP` when
constructing `Payment` directly.

## Design Reasoning

The key question was: does `CurrencyMatchValidator` need a constructor
argument at all?

The original design stored `expectedCurrency` at construction and
compared it to `account.getCurrency()` at validation time — but never
used the `payment` parameter. Once `Payment` carries its own currency,
the validator can compare `payment.getCurrency()` against
`account.getCurrency()`, which is a genuinely useful check: it ensures
the payment is denominated in the same currency as the account it is
drawn from.

Making the validator stateless also removes the awkward question of who
is responsible for creating the right validator for the right account,
which was the proximate cause of the compilation error.

## Test Updates

`PaymentTest.java` was written before `Payment` gained its `Currency`
parameter. All direct `new Payment(...)` constructor calls (15 in total)
were missing the fourth argument and failed to compile.

Each was updated to pass `Currency.GBP` as the fourth argument. The
currency choice is arbitrary for state-transition tests — these tests
are exercising `validate()`, `approve()`, `complete()`, and `reject()`,
not currency logic. Tests that go through `Account.processOutgoingPayment`
did not need changes, as the account already passes `this.currency` when
constructing the payment internally.

The `Currency` import was also added to the test file.

## Definition of Done

- `Payment` carries a `Currency` field with null validation.
- `CurrencyMatchValidator` is stateless and validates `payment.getCurrency()` against `account.getCurrency()`.
- `AccountRepository` compiles without error.
- `PaymentResponse` exposes currency.
- All 45 tests pass (`mvn test` succeeds with no failures).
